## 1차: 제출자 관점

판정 기준은 평가자가 링크만 받아 요구사항, 실행법, 구현 근거, 실패 경로를 확인할 수 있는지입니다. 과제 원문의 필수 요구와 권장 사항을 구분했습니다. Cloud Run은 허용된 배포 경로이며 Reasoning Engine 미사용 자체는 결함이 아닙니다.

### 발견 사항

| 번호 | 우선순위 | 발견 내용 | 제출 영향 |
|---|---|---|---|

### 코드 근거와 재현

**R2 — `app/static/app.js`의 승인·요청 처리**

승인 핸들러는 approve 버튼만 비활성화합니다. awaiting_approval에서 submit은 활성화된 상태이며 새 요청 핸들러는 실행을 교체합니다. 두 핸들러 모두 응답의 run ID를 현재 실행과 대조하지 않고 render합니다.

1. run A를 awaiting_approval로 표시하고 승인 응답을 지연시킵니다.
2. submit이 활성화된 상태에서 run B를 생성하고 B의 결과를 표시합니다.
3. A의 confirmed 응답을 반환하면 current.id와 결과 화면이 A로 돌아갑니다.

실제 `app.js`를 Node VM에서 실행하고 DOM·fetch 응답만 대역으로 둔 재현에서 확인했습니다. 브라우저 레이아웃 검증이 아니라 비동기 응답 순서 검증입니다. 임시 재현 파일: `.tmp/review-ui-race.cjs`.

**R3 — `skills/examflow/scripts/invoke.py`와 SKILL.md**

매 실행의 새 httpx.Client 안에서 POST /api/runs를 무조건 실행하고, --approve가 있으면 방금 생성한 run을 승인합니다. 한 프로세스 안의 세션 보존은 맞지만, 별도 호출 간 세션·run 보존은 없습니다. 처음 조회한 특정 예약안을 확인한 뒤 같은 안을 승인하는 기능과 구분해야 합니다. 다른 세션이므로 기존 세션 예약 상태도 이어지지 않습니다. 선승인한 합성 시나리오의 단일 실행은 가능하나 이를 일반적인 사후 승인 흐름으로 설명하면 안 됩니다.

**R4·R5 — 재현성**

공개 서비스용 verify_deployment.py는 별도로 제공돼 있습니다. 로컬 live_smoke.py의 개인 환경 의존성 문제와 분리해서 평가했습니다. 충돌은 tests/test_system.py의 test_conflicting_proposals처럼 같은 HTTP 세션에서 두 예약안을 먼저 만든 뒤 차례로 승인해야 합니다. 첫 예약을 확정한 뒤 같은 오후 조건을 새로 조회하면 후보가 없어져 no_slots가 될 수 있습니다.

### 내용 검토

- 두 에이전트의 책임, 조정기를 통한 A2A HTTP, 독립 MCP stdio, 모델과 결정적 규칙의 분리는 코드와 설명이 일치합니다.
- 의료적 판단 대신 합성 행정 업무로 제한한 범위는 일관됩니다. 실제 병원의 규칙·효과를 확인했다는 주장도 없습니다.
- 모델 오류 주입 시험과 실제 Gemini 관찰을 구분한 회고는 타당합니다. 공격 1개 성공 사례를 보편적 방어 성능으로 일반화하지 않았습니다.
- 두 에이전트는 조정기를 거쳐 순차 협업합니다. 독립 배포·자율 협상·모델의 자유로운 도구 계획을 구현한 것으로 확대 설명하면 안 됩니다.
- 모델은 실제로 사용되지만 합성 데이터와 오전·오후 후보가 작습니다. 데모로서 프로토콜과 경계 검증에는 적절하나 복잡한 병원 업무에서의 모델 필요성이나 성능까지 입증한 것은 아닙니다.
- PPTX 7장의 본문·노트와 문서의 숫자 및 범위를 대조했습니다. 18개 자동 테스트, 실제 Gemini 4개 사례, 공개 예약 확정이라는 기존 검증 설명과 일치합니다. PPTX 파일을 변경하지 않았으며 이번에는 PowerPoint 앱 실행이나 시각 렌더링을 다시 수행하지 않았습니다.
- 발표 대본의 합계 300초는 시간 배분입니다. 실제 낭독 시간을 측정한 결과로 표현하면 안 됩니다.
- Antigravity IDE 내 자동 발견은 기존에도 미검증으로 기록돼 있습니다. 패키지 존재와 IDE 연동 완료는 구분해야 합니다.

## 2차: 수행자 관점의 최종 검토

1차 발견 사항을 코드와 실행 결과로 다시 대조했습니다. 검토 요청의 산출물로 본 보고서와 현재 상태 문서를 갱신했으며, 애플리케이션 코드·배포·GitHub 게시는 변경하지 않았습니다. 아래 수정안은 구현 완료 내역이 아닙니다.

| 항목 | 수행자 판단 | 필요한 조치와 완료 기준 |
|---|---|---|
| R1 | 수용, 미해소 | 최종 공개 범위 승인 후 게시. 공개 main의 커밋·README·회고·스킬·PPTX 링크를 다시 조회 |
| R2 | 재현 확인, 미수정 | 승인·취소 등 변경 작업 중 새 제출 잠금, run ID 또는 요청 세대로 늦은 응답 차단. 지연 응답·중복 클릭·실패 후 복구 회귀 검증 |
| R3 | 코드 확인, 미수정 | 세션과 run을 보존하는 조회/승인 경로로 수정하거나 단일 선승인 데모로 사용법을 제한. 같은 run ID 승인 및 후보 재생성 없음 검증 |
| R4 | 코드 확인, 미수정 | 표준 ADC 또는 CLI 경로·계정 인수 지원. 개인 임시 SDK 없이 실행하는 경로 검증 |
| R5 | 문서 확인, 미수정 | API 기반 2개 예약안 준비 절차를 명시하고, 일반 UI 시연과 분리 |

### 최종 판정

**검토는 완료했지만 현 상태를 제출 준비 완료로 판정하지 않습니다.** 핵심 프로토콜과 정상 업무 흐름은 구현돼 있고 기존 테스트도 통과했습니다. 다만 공개 제출물 누락을 해소하고, 승인과 화면 전환의 경계 및 스킬의 승인 의미를 보완한 뒤 제출해야 합니다.

수정 우선순위는 R2·R3의 승인 흐름, R4·R5의 재현 안내, 관련 회귀 검증, 배포 검증, 최종 게시 순서입니다. 서비스의 로컬 DB 영속성·모델 카운터 초기화·물리 기기 미검증은 기존에 밝힌 데모 한계로 유지합니다.
