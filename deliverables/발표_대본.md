# ExamFlow 5분 발표 대본

최종 PPTX 7장 순서입니다. 시간은 발표 목표 배분이며 실제 낭독 측정값은 아닙니다. 총 300초입니다.

## 1. ExamFlow

약 25초. 검사 예약 준비 확인과 일정 조정을 구현한 ExamFlow입니다. 두 에이전트가 서로 다른 자료를 확인하고, 담당자가 그 근거를 보고 데모 예약을 확정하는 흐름입니다. 모든 데이터는 합성이며 실제 진료나 예약을 수행하지 않습니다. 이번 발표에서는 업무 범위, 프로토콜 경계, 실제 검증 결과와 배포에서 확인한 문제를 설명하겠습니다.

## 2. 검사 예약 담당자의 확인 업무

약 40초. 문제를 검사 예약 전의 행정 확인으로 좁혔습니다. 의뢰서가 접수됐는지, 연락처 확인과 담당 의료진의 사전 확인표가 있는지 살펴보고, 가능한 검사 시간을 찾는 흐름입니다. 이 규칙은 시연용으로 정의했으며 실제 병원의 운영 지침이나 임상 기준이라고 주장하지 않습니다. 자동화의 완료 조건은 답변 생성이 아니라, 확인된 근거가 예약안과 담당자 승인으로 이어지는 것입니다.

## 3. 두 에이전트와 실제 통신 경계

약 50초. 준비 확인과 일정 조정의 책임을 나눴습니다. 준비 확인이 완료돼야 일정 조정을 호출하며, 추출한 시간 선호를 전달합니다. 통신은 A2A 0.3 공식 SDK 서버와 JSON-RPC HTTP를 사용합니다. 병원 자료는 공식 MCP stdio 서버에서 조회합니다. 서비스 배포는 한 컨테이너로 단순화했지만, 내부 함수 호출을 A2A라고 표현하지 않고 실제 HTTP와 독립 도구 프로세스를 검증했습니다. 모델은 Google Gen AI SDK를 통해 Vertex AI의 Gemini를 호출합니다.

## 4. 공개 데모에서 확인한 한 요청

약 45초. 공개 Cloud Run URL에서 실행한 합성 사례입니다. 오후 예약 요청을 전달하면 준비 확인 에이전트가 접수 완료와 afternoon 선호를 반환합니다. 일정 조정 에이전트는 조회된 CT-PM, 14시를 선택합니다. 담당자의 확정 요청 후에만 MCP 예약 도구를 호출하며 confirmed 상태가 됩니다. 웹 화면 아래에서 실제 A2A Task ID와 MCP 입력 및 결과를 확인할 수 있습니다. 이 결과는 로컬 fixture가 아니라 실제 Gemini 모드로 실행했습니다.

## 5. 모델 판단과 코드 검증의 역할

약 45초. 모델이 맞는 형식으로 답하는 것과 업무적으로 올바른 것은 다릅니다. 그래서 JSON 스키마 검증 뒤에 ready와 필수 필드를 원본과 대조하고, 슬롯 ID가 조회 후보에 실제로 있는지 확인합니다. 승인과 예약 제약은 모델에 맡기지 않았습니다. AI 코딩 도구로 초안과 UI, 테스트 작성을 진행했고, 중요한 제약은 결정적인 코드로 분리했습니다. 하드 코딩을 AI 없이 타이핑했다는 의미로 쓰지 않고, 모델의 확률적인 출력에 의존하지 않는 로직이라는 의미로 설명합니다.

## 6. 서로 다른 층위에서 수행한 검증

약 45초. Python 테스트 21개는 스킬의 별도 조회와 동일 실행 승인을 포함합니다. 웹의 비동기 검사 3개에서는 중복 조작, 오래된 응답과 응답 유실 복구를 확인했습니다. 프로토콜 테스트는 실제 HTTP와 MCP를 통과하고 모델만 fixture로 고정했습니다. 실제 Gemini에서는 정상, 서류 누락, 빈 후보와 지시 우회 입력 네 시나리오를 따로 확인했습니다. 공개 Cloud Run에서는 서비스 계정 인증으로 실제 모델부터 예약 확정까지 동작을 확인했습니다. 자동 테스트에는 DB 커밋 후 응답이 유실된 상황을 주입하고, 같은 실행 번호로 재확인할 때 중복 예약이 생기지 않는지도 포함했습니다. 이 수치들은 서로 겹치는 범위를 검증하므로 합산해 총 성공률로 표현하지 않습니다. 물리 기기나 실제 병원 시스템 검증을 수행한 것은 아닙니다.

## 7. 배포에서 배운 점과 다음 단계

약 50초. 첫 Cloud Build는 기본 계정이 소스를 읽지 못해 실패했습니다. 실행 계정에 빌드 권한을 더하지 않고, 전용 빌드 계정에 소스 버킷 읽기와 이미지 저장소 쓰기, 로그 쓰기를 부여해 해결했습니다. Cloud Run은 최소 0, 최대 1 인스턴스이고 모델 호출 한도를 적용했습니다. 다만 로컬 SQLite와 메모리 기반이므로 영속성을 보장하지 않습니다. 실제 적용에서는 외부 DB와 작업 큐, 담당자 인증과 병원 규칙 검토부터 보완하겠습니다. 이번 결과물은 확인 가능한 업무 흐름과 실패 처리, 통신 근거를 갖춘 데모입니다. 감사합니다.
